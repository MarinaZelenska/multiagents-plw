# Evaluation роботи Reviewer

Ця папка — практична частина [документації агентського процесу](../docs/README.md). Сценарій заняття та [інтерактивна схема](../docs/learning-diagrams/reviewer-evaluation.html) зберігаються в `docs/`.

Практикум перевіряє, **чи Reviewer знайшов проблеми в коді й evidence**, правильно назвав їхнє місце та дав придатні до дії зауваження. Це локальні синтетичні артефакти, не кейси Notion і не фактичні запуски QAuto. Оцінювач не викликає AI, Playwright чи зовнішні сервіси.

## Що переглядати

Кожна папка `evaluation/cases/REV-XX/` містить `context.json` із локальною вимогою, CLI evidence, дозволеними файлами та симульованим результатом запуску, а також `pages/home.page.ts` і `tests/main.spec.ts`. Читайте їх як пакет для незалежного рев’ю за `docs/page-object-locators.md` і `docs/test-standards.md`. Знайдену проблему записуйте як `файл:рядок → порушення → наслідок → виправлення`.

| Сценарій | Що може побачити Reviewer |
|---|---|
| REV-01 | Чистий контрольний приклад: треба уникнути вигаданих проблем |
| REV-02 | XPath попри перевірений семантичний локатор |
| REV-03 | Дія в конструкторі й ключовий assertion у Page Object |
| REV-04 | `.first()` приховує неоднозначний локатор |
| REV-05 | Пропущене очікування та fixed wait |
| REV-06 | Неуспішний запуск і команда без `--retries=0` |

`evaluation/rules.json` містить публічні ID можливих проблем, включно з правилами, які можуть не порушуватися в обраному сценарії. Вибирайте ID з нього, не читаючи відповідь. `evaluation/golden.json` містить еталонні findings і вердикти; відкрийте його під час розбору після вправи. У формальному іспиті еталон потрібно тримати окремо від відповідей.

## Відповідь Reviewer і запуск

Для `REV-03` надішліть у чат Codex:

> Створи сабагента `reviewer` для синтетичного кейса `REV-03`. Нехай він прочитає тільки `evaluation/cases/REV-03/context.json`, `evaluation/cases/REV-03/pages/home.page.ts`, `evaluation/cases/REV-03/tests/main.spec.ts`, `evaluation/rules.json`, `docs/page-object-locators.md`, `docs/test-standards.md` і `evaluation/README.md`. Не читай `evaluation/golden.json`, `evaluation/examples/` чи попередні відповіді в `generated/`. Не викликай Notion або Playwright і не змінюй файли кейса. Поверни JSON сабагента без власних змін, з полями `scenarioId`, `verdict`, `findings`; кожне зауваження має містити `id`, `file`, `line`, `problem`, `impact`, `fix`. Збережи відповідь під новим ім’ям у `generated/` і запусти `npm run eval -- --submission <шлях до збереженого JSON>`. Покажи фактичний бал і exit code.

Для іншого сценарію замініть `REV-03` на його номер. Відповідь має містити `verdict` (`VALID` або `CHANGES REQUESTED`) та `findings`; `id` беріть із `evaluation/rules.json`, а `file` записуйте відносно папки сценарію. Якщо проблем немає, передайте порожній масив. Запуск оцінювача вручну:

```bash
npm run eval -- --submission generated/reviewer-rev03-my-run.json
```

Reviewer не запускає Playwright; локальний оцінювач читає еталон лише для підрахунку балів, не передаючи його сабагенту. Структуровані ID потрібні лише локальному оцінювачу; у звичайному рев’ю формулюйте зауваження природною мовою.

```bash
npm run eval -- --submission evaluation/examples/correct.json
npm run eval -- --submission evaluation/examples/locator.json
npm run eval -- --submission evaluation/examples/broken.json
npm run eval:check
```

Для вправи скопіюйте один JSON-приклад під новим ім’ям, змініть `scenarioId` і findings та передайте шлях через `--submission`. Код і контекст сценарію під час оцінки не виконуються. Низький бал має exit code `0`; некоректний формат або невідомий сценарій — `2`.

Для реального QAuto-рев’ю діє окремий workflow з Notion та фактичним тестовим output.

## Як рахується бал

Для сценарію з дефектами: знайдені проблеми — 45 балів, точні файл і рядок — 20, заповнені проблема/наслідок/виправлення — 15, відсутність зайвих або дубльованих зауважень — 10, вердикт — 10. Звіт показує пропущені ID, зайві ID та неправильні місця. Для чистого `REV-01` 50 балів дає відсутність хибних зауважень і 50 — `VALID`.

Автоматична оцінка перевіряє відповідність ID, місця й заповненість пояснень. Вона **не визначає, чи зміст пояснення правильний**: викладач переглядає правило, наслідок і запропоноване виправлення. Симульовані CLI й run evidence в кейсах призначені лише для цього заняття.
