# Інструкція для агентів: Page Object і локатори QAuto

Спільний контракт для Analyzer, Implementer і Reviewer. Читайте його перед створенням або перевіркою Page Object та локаторів. Межі роботи, погодження й запуски визначає `AGENTS.md`; джерела сценарію та очікувань — `docs/test-standards.md` і `docs/notion-test-cases.md`. Цей документ не надає дозволу змінювати файли поза погодженим diff.

## Обов'язки ролей

- **Analyzer:** перевіряє поточний UI через Playwright CLI, обирає локатори, записує evidence та готує Page Object у запропонованому diff. До погодження не змінює тестові файли.
- **Implementer:** застосовує погоджений diff; виправляє конкретні зауваження в дозволених межах. Для зміни локатора потрібне актуальне CLI evidence; якщо його немає, повертає запит Analyzer.
- **Reviewer:** зіставляє фактичний код із diff, джерелами очікувань і CLI evidence за чеклістом нижче. Проходження тесту саме по собі не підтверджує якість локаторів.

## Як писати Page Object

1. Спочатку перевірте наявні `pages/`: розширюйте відповідну модель, якщо вона вже описує потрібну сторінку. Не дублюйте клас для нового кейса тієї самої сторінки.
2. Розміщуйте моделі в кореневій `pages/<назва>.page.ts`, сценарії — у кореневій `tests/<назва>.spec.ts`. Не створюйте `tests/pages/`. З кореневого тесту імпортуйте модель через `../pages/<назва>.page`.
3. Один клас описує сторінку або самостійний багаторазовий UI-компонент. Назва класу — PascalCase, наприклад `HomePage`; назви полів і методів — camelCase.
4. Конструктор приймає `Page` і лише будує локатори. Не виконуйте в ньому навігацію, кліки, очікування чи інші асинхронні дії. Зберігайте `Page` у полі лише якщо він потрібний методам.
5. Імпортуйте `Page` і `Locator` як типи з `@playwright/test`. Поля локаторів оголошуйте `readonly` із типом `Locator`. Для колекції також використовуйте `Locator`; для елемента, вибраного за даними, доречний метод із поверненням `Locator`.
6. Називайте поля за призначенням елемента: `guestLogInButton`, `availableTabs`. Методи називайте за дією користувача: `open`, `loginAsGuest`, `navigateToAbout`. Уникайте `button1`, `clickButton`, універсальних `click(selector)` або `fill(selector, value)`.
7. Дії виконуйте через збережені локатори з `await`. Асинхронний метод дії повертає `Promise<void>`. Передавайте змінні дані аргументами; не вшивайте дані конкретного кейса в модель.
8. Page Object містить локатори й дії, а тест — передумови, сценарій, дані та `await expect(...)`. Відкривайте потрібні локатори для перевірок. Не ховайте ключовий expected result у методі дії та не повертайте boolean замість web-first assertion у тесті.
9. Для навігації використовуйте відносний шлях із наявним `baseURL`. Не дублюйте адресу середовища в кожній моделі.
10. Для першого прикладу не вводьте `BasePage`, singleton, власні fixtures чи універсальні wrappers. Новий клас або abstraction має вирішувати потребу поточного кейса, а не можливого майбутнього сценарію.

### Приклад форми коду

Нижче показано структуру, а не готовий diff чи підтвердження вимоги. Перед використанням локатора потрібне CLI evidence; назву тесту й assertion беріть із знайденого Notion-кейса.

```ts
// pages/home.page.ts
import type { Locator, Page } from '@playwright/test';

export class HomePage {
  readonly guestLogInButton: Locator;

  constructor(private readonly page: Page) {
    this.guestLogInButton = page.getByRole('button', {
      name: 'Guest log in',
      exact: true,
    });
  }

  async open(): Promise<void> {
    await this.page.goto('/');
  }

  async loginAsGuest(): Promise<void> {
    await this.guestLogInButton.click();
  }
}
```

У тесті створіть модель з fixture `page`, виконайте її дії та перевірте локатор відповідної сторінки через `await expect(...)`. Конкретна перевірка повинна відповідати expected result кейса; не додавайте її лише тому, що так поводиться поточний UI.

## Як обирати локатор

Обирайте вираз за поточним UI і змістом елемента, а не за припущенням про HTML.

| Елемент / умова | Переважний підхід |
|---|---|
| Кнопка, посилання, заголовок, діалог | `getByRole` із перевіреною доступною назвою |
| Поле з пов'язаною міткою | `getByLabel` із перевіреним текстом мітки |
| Елемент із наявним стабільним test ID | `getByTestId` після перевірки атрибута та налаштування проєкту |
| Текст, placeholder або alt є придатною ознакою | Відповідний `getByText`, `getByPlaceholder`, `getByAltText`, якщо ознаку підтверджено й вона однозначна |
| Придатного семантичного локатора немає | Мінімальний стабільний CSS із поясненням вибору та CLI evidence |

- Доступна назва може відрізнятися від видимого тексту через `aria-label` та інші атрибути. Перевіряйте фактичну назву, не перекладайте її й не вгадуйте.
- Коли потрібен повний збіг назви, використовуйте `exact: true`. Regex застосовуйте лише за змістовної потреби; широкий збіг не має приховувати кілька елементів.
- За повторюваних назв звужуйте область до перевіреного контейнера: діалогу, навігації, секції або рядка з потрібними даними. Контейнер також потребує evidence. Динамічний локатор будуйте з аргументу методу, а не з позиції в DOM.
- Для кліку або заповнення локатор має відповідати рівно одному потрібному елементу в цільовому стані. Колекція допустима для перевірки списку; зафіксуйте її область, склад і те, чи має порядок значення за кейсом.
- Не усувайте неоднозначність випадковими `.first()`, `.last()` або `.nth()`. Якщо позиція є частиною вимоги, підтвердьте її джерелом і CLI evidence.
- Не використовуйте XPath, довгі ланцюжки DOM, згенеровані нестабільні класи, непідтверджені CSS або snapshot refs у тестовому коді. Стабільний ID чи клас допустимий лише після перевірки та пояснення, чому семантичний локатор не підходить.
- Не додавайте test ID у product code й не змінюйте config для зручності локатора без прямого завдання користувача.

## Як підтвердити локатор через CLI

Виконуйте цей етап після знаходження точного Notion-кейса. Порядок команд і перевірку готовності визначає `qauto-cli-locators`.

1. Перевірте `npx --no-install playwright cli --version` та `npm run preflight`. За неготовності CLI, Chromium або config поверніть `CLI SETUP BLOCKER` із підготовкою за README.
2. Перший запуск: `npx playwright cli open https://qauto.forstudy.space --config=.playwright/cli.config.json`. Не передавайте CLI `playwright.config.ts`. Не виводьте вміст локального config.
3. Досягніть стану кейса через UI, отримайте `snapshot` та визначте потрібний ref. Викличте `generate-locator <ref>` у поточній сесії. Ref тимчасовий і потрібний лише для CLI.
4. Перевірте отриманий вираз у цьому стані: кількість збігів та ідентичність елемента. Один збіг не достатній, якщо це інша кнопка чи інша секція. За потреби звузьте контейнер і перевірте остаточний вираз, який увійде в diff.
5. Використовуйте команди, підтримані встановленим CLI; за потреби прочитайте його help. Не вигадуйте синтаксис. Для перевірки використовуйте Locator API через доступний механізм CLI, не окремий Browser connector.
6. Запишіть evidence для кожного нового або зміненого локатора й закрийте сесію. Якщо стан UI чи назва змінилися, отримайте нове evidence перед зміною patch.

У `templates/agent-handoff.md` передайте:

| Поле | Що записати |
|---|---|
| Контекст | Сторінка, стан / передумови, дата перевірки |
| CLI | Фактичні команди без секретів, короткий snapshot-фрагмент і ref |
| Код | Точний остаточний locator expression та поле / метод Page Object |
| Перевірка | Фактична кількість збігів, ознаки потрібного елемента; для колекції — склад |
| Обґрунтування | Причина CSS або позиційного вибору, якщо він потрібний; джерело вимоги щодо позиції |

Не копіюйте `.env`, CLI config, cookies, tokens чи credentials у evidence. **FACT** — перевірений локатор; **ASSUMPTION** — неперевірене припущення, яке не можна переносити в patch як факт. За браку evidence або суперечності кейса й UI повідомте **QUESTION** / **STOP** і blocker, а не підбирайте селектор навмання.

## Очікування під час дій

Використовуйте auto-wait дій Playwright і web-first assertions у тесті. Заборонені fixed waits, `force`, миттєве `isVisible()` як assertion та retry для маскування проблеми. Не кешуйте `ElementHandle` замість `Locator`. Якщо дія запускає навігацію чи зміну стану, перевіряйте потрібний результат за кейсом через `await expect(...)`; не додавайте довільні затримки.

## Чекліст Reviewer

- Модель лежить у `pages/*.page.ts`; сценарій — у `tests/*.spec.ts`; немає дубльованої моделі або зайвої abstraction.
- Конструктор лише ініціалізує поля; локатори типізовані `readonly`; дії мають змістовні назви, `await` і `Promise<void>`.
- Assertions і дані кейса залишилися в тесті; кожне очікування має джерело.
- Кожен новий / змінений локатор зіставляється з остаточним виразом у CLI evidence у правильному стані UI.
- Одиночні елементи однозначні; колекції мають перевірену область; CSS і позиційний вибір обґрунтовані; XPath та snapshot refs відсутні в коді.
- Немає fixed waits, `force`, boolean-перевірок замість web-first assertions або секретів.

Зауваження повертайте у форматі `файл:рядок → порушене правило → наслідок → потрібне виправлення`. Вердикт і приймання запуску визначаються загальним workflow, а не лише цим чеклістом.
