# Заняття: Analyzer → Implementer → Reviewer

Користувач задає **назву сторінки та номер кейса**. Джерело — `QAuto — База знань` у підключеному плагіні Notion. Правила — `AGENTS.md`, `docs/test-standards.md` і `docs/notion-test-cases.md`; пакет передавання — `templates/agent-handoff.md`.

## Промпт для старту

> Хочу покрити кейс TC-MP-005 по сторінці mainPage. Знайди його через плагін Notion у QAuto — База знань. Якщо кейса немає — зупинись і повідом. За потреби уточни вимоги тільки mainPage та пов'язані сутності/API. Перевір локатори через Playwright CLI і підготуй diff для погодження.

Можна коротше: `Хочу покрити кейс 5 по сторінці mainPage`. Analyzer зіставляє номер лише в таблиці цієї сторінки й повідомляє повний ID.

## Що показати студентам

1. **Analyzer** знаходить рівно один кейс, читає передумови, кроки, очікування, REQ-ID та статус. Передає case ID і посилання. Вимоги читає для уточнення лише цієї сторінки. За відсутності кейса повертає `CASE_NOT_FOUND`, не відкриває CLI й не створює diff.
2. **Analyzer** перевіряє середовище й локатори через CLI, зберігає `generated/diffs/<завдання>-v1.diff`. Назва тесту містить case ID. Показує шлях, SHA-256, вміст diff та evidence. Людина відповідає `APPROVE DIFF v1` або зауваженням.
3. **Координатор** записує `☐ В роботі — <файл> :: <назва тесту>` в колонку `Автоматизовано` вибраного кейса через плагін Notion.
4. **Implementer** застосовує patch, перевіряє TypeScript і виконує запуск тесту 1/2 із `--retries=0`. Передає фактичний output.
5. **Reviewer** одразу звіряє актуальний кейс, погоджений diff, код, CLI evidence й output. За `VALID` координатор ставить `☑` з файлом і точною назвою тесту та перевіряє запис читанням.
6. За **CHANGES REQUESTED** координатор записує статус із `☐` і повертає конкретні зауваження Implementer. Implementer зберігає виправний diff, виправляє та виконує запуск 2/2 із `--retries=0`; Reviewer перевіряє знову. Нового погодження для виправлень у тих самих межах немає.
7. Якщо після другого запуску `VALID` неможливий, координатор записує `☐ BLOCKED_AFTER_2_RUNS` із назвою тесту, зупиняє цикл і повідомляє користувачу обидва результати та причину. Третього запуску немає. Помилка синхронізації повідомляється окремо як `NOTION_SYNC_BLOCKED`.

Єдина планова точка погодження — початковий diff. Зміна кейса, вимоги чи набору файлів потребує нового diff/погодження. Усі версії diff, включно зі статусними змінами Notion, зберігаються в `generated/diffs/`.

## CLI-дослідження

Лише після знаходження кейса Analyzer відкриває UI:

```bash
npx playwright cli open https://qauto.forstudy.space --config=.playwright/cli.config.json
```

Далі використовує `snapshot`, refs, `generate-locator <ref>` і `close` у тій самій сесії. У handoff передає безпечне evidence; секрети й локальний config не виводить. За неготового CLI, Chromium чи config — `CLI SETUP BLOCKER` і кроки підготовки з README.

## Критерії розбору

- Реалізований саме вибраний case ID; усі його очікування мають assertions, Page Object містить локатори та дії.
- Кожен locator має CLI evidence; кожен expected result — джерело в кейсі або вимогах вказаної сторінки.
- Фактичні файли відтворюються з початкового й виправних diff у `generated/diffs/`.
- Не більше двох запусків, кожен із `--retries=0`, номером, exit code та фактичним output.
- `Автоматизовано` відповідає вердикту й містить точну назву тесту. Це текстові позначки `☐`/`☑` у звичайній таблиці; технічні деталі в `docs/notion-test-cases.md`.

Завершений приклад попереднього флоу можна розібрати за `generated/diffs/guest-garage-v1.diff`. Це історичний diff: локальне джерело вимоги та Garage-тести з того проходження видалено, а для нового завдання потрібен кейс у Notion.
