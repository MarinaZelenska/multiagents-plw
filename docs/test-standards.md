# Стандарти Playwright-тестів для QAuto

Цей документ є спільним контрактом для Analyzer, Implementer та Reviewer. Пріоритет мають погоджена вимога і `AGENTS.md`. Agent не є джерелом очікуваного результату.

## Від вимоги до перевірки

Користувач передає назву сторінки й номер кейса. Основне джерело — точний рядок у `QAuto — База знань → Тест-кейси → <сторінка>` через плагін Notion за `docs/notion-test-cases.md`. Якщо кейса немає — `CASE_NOT_FOUND` і зупинка, без підміни іншим джерелом. Для уточнення дозволені вимоги тільки вказаної сторінки, за потреби — пов'язані сутності та API-операції.

Для кожного тесту визначте початковий стан, дані, усі кроки та очікування вибраного кейса. Біля кожного assertion у handoff зазначте case ID / REQ-ID, URL та використаний фрагмент. Назва `test()` містить повний case ID, наприклад `TC-MP-005 — <поведінка>`; handoff містить точні файл і назву тесту. Спостереження в UI підтверджує локатор і поточну поведінку, але не створює нову вимогу. Без джерела критичного очікування або за суперечності джерел — `CASE_SPEC_BLOCKED`.

## Page Object

Перед створенням або рев'ю моделі прочитайте [інструкцію для агентів: Page Object і локатори](page-object-locators.md). Вона визначає структуру класів у `pages/`, межі між моделлю й тестом, типізацію, назви та приклад коду.

## Локатори та CLI evidence

Вибір локаторів, перевірка однозначності через Playwright CLI й формат evidence визначені в [інструкції для агентів](page-object-locators.md). Analyzer читає її до підготовки diff, Implementer — перед застосуванням і виправленням, Reviewer — перед перевіркою коду.

## Тест і запуск

- Один незалежний тест на один сценарій; використовуйте fixture `page`, `baseURL` і Arrange–Act–Assert. Підготовка стану не повинна приховувати перевірку головного результату.
- Використовуйте auto-wait Playwright і web-first `await expect(...)`. Не додавайте fixed waits, `force`, `isVisible()` як миттєву перевірку чи retries для маскування проблеми.
- Для окремого кейса вказуйте файл, project і `--grep`, який зіставляється з повною назвою Playwright: project, файл, вкладені suite та назва тесту. Не ставте `^` перед самою назвою `test()`: перед нею є префікс. Приклад для цього проєкту: `npx playwright test tests/main-page.spec.ts --project=chromium --grep 'TC-MP-003 — Перехід до секції About$' --retries=0`. Екрануйте regex-символи в назві та переконайтеся статично, що в обраному файлі фільтр відповідає рівно одному тесту. Analyzer передає цю команду в handoff; Implementer звіряє її перед запуском.
- Перед запуском браузера врахуйте дозволи середовища. У поточному macOS Codex sandbox вже підтверджено `bootstrap_check_in ... Permission denied (1100)` і `SIGTRAP` при запуску Chromium. Для наступного Playwright Test у цьому середовищі одразу запитуйте дозволений запуск команди через `sandbox_permissions: "require_escalated"`; після отримання дозволу виконуйте її як одну з двох спроб. Налаштування Playwright не усувають цю заборону ОС. Якщо ескалацію відхилено, повідомте blocker до тестового запуску; не запускайте ту саму команду у відомо несумісному sandbox. На інших середовищах обирайте режим за наявними evidence. Помилка вже виконаної команди витрачає спробу, а вичерпаний ліміт не дозволяє повторення з ескалацією.
- Після застосування погодженого diff Implementer перевіряє TypeScript і запускає окремий Playwright Test у тому самому етапі з `--retries=0`. На одне завдання дозволено щонайбільше два виклики команди Playwright Test: перший після реалізації, другий після виправлення зауважень або діагностики failure. Невдалий виклик через середовище теж зараховується; Playwright CLI, preflight, TypeScript і читання report/trace — ні. Config не змінюйте.
- У evidence для запусків 1/2 та 2/2 вкажіть точні команди, exit codes і дослівні підсумки. Після другого запуску без `VALID` зупиніть автоматичні виправлення й повідомте користувачу `BLOCKED_AFTER_2_RUNS`, причину та обидва результати. Третій запуск потребує нового завдання користувача.
- Failure досліджуйте через локальний report/trace. Не оголошуйте його дефектом продукту до встановлення причини. Не виводьте `.env`, CLI config, cookies, tokens або credentials.

## Рев'ю та приймання

Кожен запропонований або виправний unified diff зберігайте окремим файлом у `generated/diffs/` за шаблоном `<назва-завдання>-vN.diff`. Посилання на файл і SHA-256 передавайте між ролями. Не перезаписуйте попередню версію. Початковий diff потребує `APPROVE DIFF vN`; виправлення конкретних зауважень Reviewer у межах тієї самої вимоги й файлів виконуються без нового погодження. Зміна вимоги або набору файлів потребує нового diff і погодження.

Reviewer після реалізації звіряє фактичні файли з початковим і виправними patch, assertion із джерелом, locator із CLI evidence, межі файлів і фактичний output. Формат зауваження: `файл:рядок → порушене правило → наслідок → потрібне виправлення`. Після першого запуску зауваження одразу передаються Implementer для виправлення й повторного рев'ю. Фінальні стани: `VALID`, `CHANGES REQUESTED`, `BLOCKED`, `BLOCKED_AFTER_2_RUNS`.

Перед `VALID` Reviewer звіряє актуальний кейс у Notion із handoff і перевіряє повноту покриття. Зміна сценарію — `CASE_CHANGED`, а не автоматичне переписування expected result. Координатор оновлює тільки `Автоматизовано` за `docs/notion-test-cases.md`: `☑ <файл> :: <назва тесту>` після підтвердженого успіху або `☐ <статус> — <файл> :: <назва тесту>` при невдачі. Запис перевіряється читанням; за проблеми — окремий `NOTION_SYNC_BLOCKED`, без третього запуску тесту.
