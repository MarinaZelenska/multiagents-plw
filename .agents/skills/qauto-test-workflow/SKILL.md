# QAuto test workflow

Прочитай `AGENTS.md`, `docs/test-standards.md`, `docs/notion-test-cases.md` і `templates/agent-handoff.md`. Вхід — назва сторінки й номер кейса. Веди один пакет передавання з повним case ID, URL/ID Notion-сторінки та джерелами. Делегуй Analyzer етап: `qauto-notion-cases` → точний кейс у `QAuto — База знань` → за потреби вимоги тільки цієї сторінки, пов'язані сутності/API → preflight → Playwright CLI → evidence → diff у `generated/diffs/`. За `CASE_NOT_FOUND` зупинись і повідом користувачу; не запускай інші ролі. За недоступності плагіна чи неповних даних поверни blocker, без окремого MCP або іншого каналу доступу.

Покажи людині шлях, SHA-256 і вміст diff разом із case ID, джерелами, точними файлом і назвою тесту. Це єдина планова точка погодження; після `APPROVE DIFF vN` передай файл Implementer і синхронізуй у Notion `☐ В роботі — <файл> :: <назва тесту>` за `qauto-notion-cases`.

Implementer застосовує diff, виконує TypeScript-перевірку та перший запуск окремого Playwright Test з `--retries=0`. Одразу делегуй Reviewer перевірку коду й фактичного output. За `VALID` синхронізуй Notion, потім поверни користувачеві вердикт і evidence. За `CHANGES REQUESTED` після першого запуску синхронізуй статус і автоматично передай конкретні зауваження Implementer; він зберігає новий виправний diff у `generated/diffs/`, виправляє й виконує другий запуск тесту з `--retries=0`, після чого Reviewer перевіряє знову. Не запитуй нового погодження для виправлень у межах погодженої вимоги та файлів. Якщо ці межі треба змінити, поверни роботу Analyzer для нового diff і погодження; лічильник запусків цього завдання не скидай.

Рахуй кожен виклик команди Playwright Test у межах завдання, включно з помилками середовища: максимум два. Вимикай внутрішні retry прапорцем `--retries=0`, не змінюючи config. Preflight, CLI-дослідження, TypeScript, report/trace і статичне рев'ю до ліміту не входять. Якщо після другого запуску немає `VALID`, зупини автоматичний цикл і повідом користувачу `BLOCKED_AFTER_2_RUNS`, обидві команди, exit codes, фактичні підсумки й причину. Третій запуск можливий лише за новим завданням користувача.

Не запускай ролі, які одночасно змінюють ті самі файли. За відсутності джерела expected result або CLI evidence поверни blocker; не підміняй його здогадом. Не проси окремих `APPROVE SPEC`, `APPROVE CLI INSPECTION`, `APPROVE RUN` чи фінального `ACCEPT`.

Після кожного вердикту Reviewer сам синхронізуй лише комірку `Автоматизовано` цільового кейса за `docs/notion-test-cases.md`. Тільки `VALID` з passing-run поточного коду дає `☑` і точну назву тесту. Після `BLOCKED_AFTER_2_RUNS` спочатку спробуй записати цей статус із `☐`, потім повідом користувачу. Підтверджуй запис повторним читанням; за проблеми поверни результат тесту та окремий `NOTION_SYNC_BLOCKED`, без третього запуску. Записи Notion виконує лише координатор через плагін; додатковий людський approval не потрібний.
